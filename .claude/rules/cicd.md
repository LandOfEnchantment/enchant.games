# CI/CD

How a change reaches `master` and the live site (2026-10-11). The same road as ../adamschaefers.com (its `.claude/rules/cicd.md`): the merge is the deploy, CI is the build of record, no secret on a pull request, every deploy checks itself. Before it, GitHub Pages served `master`'s files as they were, a git pre-commit hook built the manifests into commits, and the libraries were vendored under `js/`.

## The road to master

- `master` takes no direct push: the ruleset (`terraform/github.tf`) wants a pull request, `check` and Terraform's `plan` green (from GitHub Actions, app 15368, so a status of that name from anywhere else satisfies nothing), and one approval; a push dismisses a stale approval. No force push, no deletion. Not strict: a pull request need not be on the newest `master` (the merge's own check runs again before it deploys). No bypass actor.
- Auto-merge for the owner and the Claude sessions the owner drives, nobody else. `owner-merge.yml` (`pull_request_target`) approves a pull request whose author and event sender are user id 26800291 (a-schaefers), from this repository, not a draft, at the head it was woken for, then arms auto-merge if nobody has. Anyone else's (other people, other Claudes, Dependabot, forks) waits for the owner's approval by hand; so does the owner's own after someone else pushes to it, until the owner pushes again. A draft holds one back.
- `owner-merge.yml` must never run the pull request's code: no checkout, no `uses:`, nothing from the event in a shell but the number, the head hash, the repository and the token. `scripts/test_workflows.py` (in `make check`) holds it to that.
- Who arms auto-merge decides whether the merge deploys at once: a merge armed with the workflow's token is GitHub Actions' push, which starts no workflow. `scripts/ship.sh` arms it as the owner, so the merge is the owner's and `deploy.yml` runs on it; when `owner-merge.yml` armed it (or merged it), that job waits for the merge and dispatches `deploy.yml`, the one run its token may start, so every merge deploys at once (owner, 2026-10-12); the hourly run is the safety net.

## Shipping

- Commit on a branch (or in a worktree), then `scripts/ship.sh`: pushes `HEAD` to the branch (a detached `HEAD` ships as `agent/<worktree>`), opens the pull request or finds the open one, arms auto-merge as you with `--match-head-commit`, waits for the merge or names the failing check. It refuses to ship from `master`. `--draft` opens one that waits. A red check leaves auto-merge armed: fix, commit, run it again.
- Never commit `public/` (the pages, `rss.xml`, `sitemap.xml`, `version.json`): `make build` writes it, git ignores it, CI builds it.

## Workflows

- `check.yml`, the required check: `npm ci`, then `make check` (`scripts/build.js` draws every page into `public/`; `scripts/check-dist.js` checks every page and article is drawn at its address with its title, every link and picture that points at the site itself, and that none uses an old `?slug=` address; `scripts/test_workflows.py`), then uploads `public/` as the `github-pages` artifact. On every pull request, no secret, no path filter (never rename the job without the ruleset; the same for terraform.yml's `plan`, required since 2026-10-12).
- `deploy.yml`, on every push to `master` (and hourly, and by hand): `check.yml` again on the merged commit, then in the `github-pages` environment (master only): `actions/deploy-pages` publishes that artifact (the job's OIDC token) and waits until GitHub says it is live; only then `scripts/purge.js` clears Cloudflare's copy of every address the build serves, bare and keyed (`CLOUDFLARE_API_TOKEN`, given to that step alone; a purge before the publish would refill the new keys with the old files); then `scripts/smoke.sh` asks with nonce probes (`?probe=<commit>-<attempt>-<random>`, an address no cache has seen) until the home page, the journal, the script and `version.json` are this build's, then that a page, an article, the feed and the sitemap answer, an unknown address gets 404, and the old `?slug=` addresses 301 to the new. It never fetches a keyed address. Deploys never overlap and are never cancelled. The hourly run stops when the newest `github-pages` deployment is already `master`'s.
- `terraform.yml` (2026-10-12, as ../merecatholicity.com's): `terraform/` is the repository's GitHub settings and the zone's Cloudflare configuration (`terraform/README.md`). Every pull request: `fmt` and an offline `validate`, no credentials (every secret blanked on a `pull_request` event in its own expression). A merge that changes `terraform/` (or a run by hand): `plan` with the repository secrets `CLOUDFLARE_ROOT_TOKEN` and `GH_ROOT_TOKEN`, the state in R2 (`enchant-games-tfstate`, its S3 pair derived from the Cloudflare token), and when it has changes, `apply` waits on the `terraform-production` environment for the owner's review (the browser, or `scripts/ci_approve.sh`), re-plans, and refuses a plan other than the one reviewed. It never prints a plan or uploads the plan file (this repository's logs are public; state holds secrets): reviewers see `scripts/tf_plan_summary.py`. A destroy or replace fails the plan unless dispatched with `allow_destroy`.
- `purge-cache.yml`, by hand only: empties Cloudflare's whole cache of the zone without a deploy (`scripts/purge.js --everything`), waiting for any running deploy.
- Every `uses:` names a commit with a `# vX.Y.Z` comment; `.github/dependabot.yml` bumps the action pins and the npm packages weekly, each pull request waiting for the owner.

## Cache busting

As in ../merecatholicity.com (2026-10-11). Every file a page asks for carries `?v=<the first 32 bits of its sha256, as a number>`, stamped by `scripts/build.js` in dependency order (the font into `style.css`; then the script, `style.css`, the icon, the font and the pictures into every page it draws). Content alone decides a key, so a rebuild changes nothing and nobody bumps one by hand; `scripts/check-dist.js` fails on any key that isn't its file's. Unkeyed on purpose: the pages, `version.json`, `rss.xml`, `sitemap.xml`. `version.json` (`{build, assets}`) names the keys every page loads; `js/version.js` compares it, fetched no-store, with the keys the open page is running (read off its own `<script>`/`<link>` addresses), on returning to the tab and hourly, and offers Reload; it never reloads by itself, nor over a half-written form (`scripts/version.test.js`). Cloudflare: Browser Cache TTL respects the origin (GitHub's ten minutes), and keyed files get a day in the browser (`terraform/zone.tf` and `terraform/rulesets.tf`; it was 4 hours on everything before, which no purge could reach).

## Prerendered (2026-10-12)

Until then the site was one `index.html` whose script (lit-html, marked and js-yaml, 100 KB) fetched `pages.json` and every page's YAML and drew the page in the browser, at `/?slug=<page>` addresses. Now `scripts/build.js` draws each page and article once, in CI, into its own HTML file at its own address, and the browser's script is 10 KB; once the first page is up, `js/nav.js` fetches the rest in the background and swaps them in place, so only the first page waits on the network. Every address the site ever had lands somewhere live: retired pages and articles forward per `redirects.yml` (the build refuses a `disabled/` page without an entry), and `make old-links` proves it in a real browser against the live site. The old addresses stay good: four redirect rules (`terraform/rulesets.tf`) 301 them (`/?slug=<page>` to `/<page>/`, `/?slug=journal&article=<slug>` to `/journal/<slug>/`), and the home page's head sends on any they miss; the feed keeps each article's old address as its `guid`, so no reader sees an old article as new. The font came from Google Fonts' copy, vendored; it is now `firacode` from npm, its `@font-face` overriding the vertical metrics to the old copy's so no line moved.

## Settings

- Terraform (`terraform/`, its README) since 2026-10-12, when it adopted what `scripts/github-settings.sh` and `scripts/cloudflare-settings.sh` held: the ruleset; the workflow token read only and allowed to approve pull requests (and the LandOfEnchantment organization allowing that); auto-merge, merge commits, delete branch on merge, update branch; only GitHub-owned and verified actions, each pinned to a commit; secret scanning with push protection; Dependabot alerts and security fixes; GitHub Pages built by Actions at enchant.games; the `github-pages` environment (master only) and the `terraform-production` gate (master only, the owner's review, no admin bypass); the zone id variable; and on Cloudflare the zone's settings, DNS, cache and redirect rules, bot management, the mailing list's widget and database, Web Analytics (off) and the state bucket. The one setting the provider can't hold, a fork's workflows waiting for approval every time, stays set by hand (`terraform/README.md`).
- The three sites' Terraform never share a resource: this one owns enchant.games' zone, repository and objects; ../merecatholicity.com's and ../adamschaefers.com's own theirs (nothing of one site serves another: since 2026-10-12 the Press page's contact form has its own Worker and widget, no longer adamschaefers.com's); the account, its tokens, its Email Routing destination and its Zero Trust organization are nobody's. So an apply in one never shows as drift in another.
- Secrets, set by hand and never in Terraform: `CLOUDFLARE_API_TOKEN` in the `github-pages` environment (deploy.yml's purge) and `CLOUDFLARE_ROOT_TOKEN` at the repository (terraform.yml), both the account-wide Cloudflare token ../merecatholicity.com's pipeline uses (`CLOUDFLARE_ROOT_TOKEN` in `~/.config/merecatholicity/ci.env`); a hobby account, one token. `GH_ROOT_TOKEN`, a classic token the owner minted on 2026-10-12 for this pipeline and ../adamschaefers.com's (`~/.config/hobby/github-token`). Rotating one means every copy (`terraform/README.md`).
- Actions may approve pull requests only because the owner is the one collaborator: anyone else with write access could approve their own pull request through a workflow on their branch. Revisit before granting anyone write access to LandOfEnchantment (dontNedd, the other member, has read).
- The emergency door: when `check` itself is broken and its fix cannot pass it, the owner sets the ruleset's enforcement to `"disabled"` (Settings, Rules; the next plan shows it as drift until it is set back, or set it in `terraform/github.tf` and apply), merges the fix, and sets it back. Never a bypass actor.

## Done by hand, on purpose

- Cloudflare proxies enchant.games in front of GitHub Pages (DNS, TLS). The zone's configuration is Terraform's (above), applied only through `terraform.yml`'s gate.
- The contact form Worker, `enchant-games-contact` (`contact-worker/`, routed at `enchant.games/api/contact`; 2026-10-12, when the Press page stopped sharing adamschaefers.com's): `make contact-deploy` deploys it, by hand, with the same token; CI runs its tests (`make test`); deploy a change to it before (or with) the pages that need it. It emails the owner's verified Email Routing destination from `contact-form@enchant.games`. Its `TURNSTILE_SECRET` belongs to the widget "enchant.games contact form" (enchant.games only).
- The mailing list Worker, `enchant-games-signup` (`signup-worker/`, routed at `enchant.games/api/signup` and `/api/unsubscribe`; 2026-10-12): `make signup-deploy` applies its D1 migrations and deploys it, by hand, with the same token. CI only runs its tests (`make test`); a merge doesn't deploy it, so deploy a change to it before (or with) the pages that need it. Its `TURNSTILE_SECRET` belongs to the Turnstile widget "enchant.games release signup" (enchant.games only); the database `enchant-games-signups` holds the addresses, each with the wording it agreed to (`consent`), and nothing reads them. A change to the consent wording is a change to `js/signup.js`, the Worker's `CONSENT` and a migration naming it, deployed Worker-last: the old Worker stores the new form's signups as `releases`, the safe side, for the minutes between.
